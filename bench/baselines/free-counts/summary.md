## What this decides

### Zero-decode thumbnails

The count supports a narrow build only. Of 131 JPEGs, 66 carry an EXIF thumbnail, and 43 can serve a 160 px request from it without a stale picture by the rule above. That is about a third of this corpus. For those 43, a 160 px request reads a median 1,443,161 entropy bytes today (range 12,025 to 3,764,897), which is what a served thumbnail would avoid. The staleness rule is the constraint. Eleven of 66 thumbnails fail it, and a header-only aspect check, which reads only the two frame headers, catches ten of the eleven. The one it misses (145712499, 19.95 dB, 0.00 percent aspect) sits on the PSNR line, so a build would need the PSNR check or an explicit decision to accept that case. The PSNR is measured against a box-filtered main image, so it shows that a thumbnail depicts the same picture. It does not show that the thumbnail looks as good as a 160 px resample from tinyimg, and nothing here measures that. The AVIF `thmb` half is not decided. The corpus holds no `thmb` item, since avifenc writes none and the two fixtures have none, so the zero says nothing about camera output. All of these JPEGs are Commons uploads, so the one-third is a Commons rate, not a phone rate. A sample of phone JPEGs and camera AVIFs is what would decide the rest.

### Progressive JPEG at 1/8

Do not build the planned mechanism, because its byte-exact part already exists. Of 131 JPEGs, 25 are progressive. At 1/8 the decoder already steps over the luma AC scans on all 25 (median 0.751 of file bytes, range 0.431 to 0.966), and the `scansSkipped` counter records it. The plan said no DC-only early-out was found, and the counter shows one, so that premise is wrong. What remains at 1/8 is chroma AC on the 16 files with 2x2 luma sampling, a median 0.121 of file bytes (range 0.033 to 0.247). The 4:4:4, 4:2:2 and grayscale files already read DC only. Skipping the 4:2:0 chroma AC would change the output pixels, so it is a lossy lever for the FAST tier, and this count takes no quality measure. The 160 px request the plan named reaches 1/8 for only 12 of the 25. Twelve progressive files are narrower than 1280 px, and one 1280 px file fails on its rounded height. Across all 25, a 160 px request reads a median 0.923 of file bytes (range 0.030 to 0.998). The 1200 px request runs out of memory on two of the 25, both over 7 megapixels, in the shipped module's 64 MiB heap; one of the two fails even in a fresh instance. Neither mechanism touches that, because the DC-only path only applies at 1/8. Sixteen 4:2:0 files are too few to decide the lossy chroma question. A set of progressive 4:2:0 photographs scored against the full decode would decide it.
